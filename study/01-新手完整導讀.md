## 1. 這個專案到底是什麼？（一分鐘版）

想像一個倉庫：有一台小車，前面有兩根叉子（像堆高機），它要自己：

1. **認識環境**：先被人遙控繞一圈，邊走邊畫出倉庫的平面地圖。
2. **記住要去的點**：操作員在手機網頁上把「取貨點」「放貨點」存起來。
3. **自己規劃路線**：算出一條不會撞牆、最短的路。
4. **自己開過去**：沿路走；如果前面突然有人或箱子擋住，**停下來等**，障礙移開再沿**同一條路**繼續走（比賽規定不能繞道）。
5. **搬貨**：叉子升降，把貨叉起來或放下。

這台車叫 **Nebula**。真車上的大腦是 NVIDIA Jetson 小電腦，輪子由 Arduino Mega 控制，叉子升降由 ESP32 控制。

**重點**：這個 GitHub repo **沒有**放真車的全部程式（比賽相關細節作者保密），
它放的是一個**可以在電腦上跑的模擬版本**：

- 機器人的 3D 模型（尺寸、輪子、雷射掃描器、IMU、叉子）
- 一個模擬比賽場地（牆、分區、地上的 QR 碼）
- 兩支 Python 程式：**行為樹自主節點**、**雷射掃描過濾節點**
- 一整套導航設定（建地圖用 SLAM Toolbox、導航用 Nav2）

所以這個 repo 的定位是：**「用模擬器展示整套自主移動機器人的架構」**。

## 2. 先備知識速成（看程式之前一定要懂的觀念）

### 2.1 ROS 2 是什麼？

**ROS（Robot Operating System）** 不是真的作業系統，而是一套**讓很多小程式互相傳訊息的框架**。
寫機器人時，你不會寫一支超大程式包辦一切，而是拆成很多小程式，每支只做一件事：

- 一支讀雷射掃描器
- 一支算機器人在哪裡
- 一支規劃路線
- 一支控制馬達

ROS 2 負責讓它們彼此溝通。本專案用的是 **ROS 2 Humble**（2022 年發布的長期支援版，搭配 Ubuntu 22.04）。

### 2.2 ROS 2 的六個核心名詞（一定要背）

| 名詞 | 白話解釋 | 生活比喻 | 本專案的例子 |
| --- | --- | --- | --- |
| **Node（節點）** | 一支正在執行的小程式 | 公司裡的一個員工 | `scan_filter_node`、`amr_behavior_tree` |
| **Topic（話題）** | 一個有名字的訊息頻道，一方發、多方收 | 公司群組裡的一個頻道 | `/scan`、`/cmd_vel`、`/odom` |
| **Message（訊息）** | 在 topic 上傳的資料，格式固定 | 頻道裡的一則貼文 | `LaserScan`、`Twist`、`Float32` |
| **Publisher / Subscriber** | 發訊息的人／訂閱收訊息的人 | 在頻道發文的人／開通知的人 | 過濾節點**訂閱** `/scan`、**發布** `/scan_filtered` |
| **Action（動作）** | 需要花時間、會回報進度、可以取消的任務 | 叫外送：下單→途中回報→送達 | `action/PlayAudio.action`；Nav2 的「導航到某點」 |
| **Launch 檔** | 一次啟動很多節點的腳本 | 開店 SOP：一鍵開燈開冷氣開收銀機 | `launch/gazebo.launch.py` |

另外兩個常用的：

- **Parameter（參數）**：節點的設定值，例如最高速度 0.26 m/s。寫在 `config/*.yaml` 裡。
- **Package（套件）**：一個資料夾，裝一組相關的節點、設定、模型。**整個 repo 就是一個叫 `amr_forklift` 的套件**。

### 2.3 座標系與 TF（機器人最容易搞混的地方）

機器人身上每個零件都有自己的座標系（叫 **frame**）。例如雷射掃描器說「前方 2 公尺有牆」，
這個「前方」是**掃描器自己的前方**。要知道牆在地圖上哪裡，就要一路換算：

```
map（地圖原點）
 └─ odom（里程計原點：開機那一刻機器人的位置）
     └─ base_footprint（機器人正下方地面上的點）
         └─ base_link（車身中心）
             ├─ lidar_link（雷射掃描器）
             ├─ imu_link（慣性感測器）
             ├─ left_wheel_link / right_wheel_link（左右驅動輪）
             ├─ caster_*（四個萬向輪）
             ├─ left_sensor_link / right_sensor_link（前方兩個測距感測器）
             └─ forklift_mast_link（叉架）
                 └─ forklift_carriage_link（可升降的叉子）
```

**TF（Transform）** 就是 ROS 用來記錄「誰在誰的哪裡」的系統。重點：

- `map → odom`：由 **SLAM** 或 **AMCL**（定位）算出來
- `odom → base_footprint`：由**輪子里程計**（或 EKF）算出來
- `base_footprint → 其他零件`：固定不變，由 `robot_state_publisher` 讀機器人模型發出來

**為什麼要分 map 跟 odom 兩層？** 輪子會打滑，里程計走久了一定會偏（叫「漂移」）。
odom 是「短時間很準、長時間會偏」；map 是「透過雷射比對牆壁，定期把偏掉的部分拉回來」。

### 2.4 機器人學六個關鍵概念

| 概念 | 白話解釋 | 本專案怎麼用 |
| --- | --- | --- |
| **差速驅動（Differential Drive）** | 左右兩個輪子各自控制速度。兩輪同速＝直走；一快一慢＝轉彎；一正一反＝原地轉 | Nebula 中間兩個驅動輪、四角四個萬向輪 |
| **里程計（Odometry）** | 數輪子轉了幾圈，推算自己走了多遠、轉了幾度 | 模擬時由 Gazebo 外掛發到 `/odom` |
| **IMU（慣性測量單元）** | 量角速度與加速度的晶片（手機也有），轉彎角度比輪子準 | 模擬 IMU 發到 `/imu/data_raw` |
| **LiDAR（雷射掃描器）** | 轉一圈射雷射，量四周每個角度的距離 | 360 點、最遠 10 公尺、每秒 10 次，發到 `/scan` |
| **SLAM（同時定位與建圖）** | 一邊走一邊畫地圖，同時知道自己在地圖哪裡 | 用 **SLAM Toolbox** |
| **路徑規劃** | 全域規劃（整條路怎麼走）＋局部控制（下一瞬間方向盤怎麼打） | 用 **Nav2**：NavFn 全域規劃器＋DWB 局部控制器 |

### 2.5 其他你會遇到的工具

| 工具 | 是什麼 |
| --- | --- |
| **Gazebo** | 3D 物理模擬器。有重力、摩擦力、會模擬感測器。讓你不用買真車也能測試 |
| **RViz** | 視覺化工具。把地圖、雷射點、機器人位置、規劃的路線畫出來給人看。**RViz 只「看」，不模擬物理** |
| **URDF／Xacro** | 描述機器人長相與關節的 XML 檔。Xacro 是加了「變數與巨集」的 URDF，可以少寫很多重複內容 |
| **SDF／.world** | 描述模擬世界（地板、牆、燈光）的檔案 |
| **colcon** | ROS 2 的編譯工具，`colcon build` 把套件建置好 |
| **行為樹（Behavior Tree）** | 一種「決定現在該做什麼」的樹狀邏輯，遊戲 AI 也常用。本專案用 Python 套件 **py_trees** |
| **EKF（擴展卡爾曼濾波）** | 把多個不準的感測器（輪子＋IMU）融合成一個比較準的估計 |
| **Costmap（代價地圖）** | 地圖上每格標「多危險」：牆是 254、牆邊緩衝區逐漸變低、空地是 0。規劃器挑代價低的路走 |

## 3. 真車的系統架構（為什麼要分三層）

作者把系統分成三層，**依「反應時間要求」切開**：

```
┌────────────────────────────────────────────────┐
│ 第 1 層：操作介面（手機/平板瀏覽器網頁）         │
│   建圖、教點、看即時地圖、手動遙控               │
└───────────────┬────────────────────────────────┘
                │ WiFi
┌───────────────▼────────────────────────────────┐
│ 第 2 層：大腦 NVIDIA Jetson（ROS 2 Humble, Docker）│
│   SLAM、EKF 定位、Nav2 規劃、行為樹、障礙守衛   │
│   （重運算，延遲幾十毫秒沒關係）                 │
└───────┬───────────────────────┬────────────────┘
        │ USB 序列埠             │ WiFi / TCP
┌───────▼──────────┐   ┌────────▼─────────────────┐
│ 第 3a 層：Arduino Mega │   │ 第 3b 層：ESP32          │
│ 驅動輪馬達 20kHz PWM │   │ 叉子升降機構             │
│ 編碼器、IMU、電流   │   │                          │
│（毫秒級即時控制）  │   │                          │
└──────────────────┘   └──────────────────────────┘
```

**為什麼不全部塞在 Jetson？** 規劃路線這種重工作會讓 CPU 忙不過來，
如果馬達控制也在同一顆處理器上，馬達就會「卡頓」。所以即時性要求高的交給單晶片。

> 這三層裡，**repo 裡只有第 2 層的「模擬版」**。Arduino、ESP32 韌體與網頁介面都不在 repo 裡。

## 5. 逐檔精讀

### 5.1 `package.xml`——套件的身分證

它告訴 ROS：「我叫 `amr_forklift`，我需要 `rclpy`（Python 版 ROS 函式庫）、`geometry_msgs`、
`sensor_msgs`……才能跑。」建置類型是 `ament_cmake`（用 CMake 建置，同時也安裝 Python 程式），
因為它要**產生自訂的 Action 訊息**，這件事純 Python 套件做不到。

### 5.2 `CMakeLists.txt`——建置說明書

做四件事：

1. 把 `amr_forklift/*.py` 安裝成 Python 模組。
2. 把兩支 Python 檔安裝成「可執行檔」，並**改名去掉 `.py`**：
   `amr_behavior_tree.py` → `amr_behavior_tree`。所以 launch 檔裡寫 `executable='amr_behavior_tree'`。
3. 把 `launch`、`worlds`、`models`、`rviz`、`config`、`maps` 這些資料夾複製到安裝目錄的 `share/amr_forklift/`。
   launch 檔用 `get_package_share_directory('amr_forklift')` 找到它們。
4. 用 `rosidl_generate_interfaces` 把 `PlayAudio.action` 編譯成 Python／C++ 可以用的類別。

> ⚠️ 第 1 點把路徑寫死成 `python3.10`。Ubuntu 22.04（Humble）沒問題；
> 在 Ubuntu 24.04（Jazzy，Python 3.12）上這個模組會裝錯地方，但因為 launch 用的是第 2 點裝好的可執行檔，**不影響執行**。

### 5.3 `action/PlayAudio.action`——自訂 Action

Action 檔用 `---` 分成三段：

```
目標（Goal）     ：要播哪個音效、音量、播多久、要不要循環、要不要打斷目前的聲音、優先權
---
結果（Result）   ：有沒有接受、訊息、用哪個喇叭
---
回饋（Feedback） ：已經播了幾秒、目前狀態（waiting/playing/stopped/canceled/error）
```

真車大概用它來播「注意，機器人移動中」之類的提示音。**repo 裡沒有任何程式使用它**，只是定義。

### 5.4 `amr_forklift/scan_filter_node.py`——雷射盲區過濾（最簡單，建議第一個讀）

**要解決的問題**：雷射掃描器裝在車身中央上方，往前看會看到**自己的叉架兩根柱子**，
導航系統以為前面有障礙物，就不敢往前走。

**解法**：把那兩根柱子所在的角度範圍的距離值，改成「無限遠」（`inf`），等於「那個方向什麼都沒有」。

```python
# 左柱子大約在 +16.3°（0.284 弧度），過濾 0.22～0.35 弧度
# 右柱子大約在 -16.3°，過濾 -0.35～-0.22 弧度
for i in range(len(ranges)):
    angle = msg.angle_min + i * msg.angle_increment   # 第 i 個點的角度
    ...                                                 # 把角度正規化到 -π～π
    if 在左柱範圍 or 在右柱範圍:
        ranges[i] = float('inf')
```

**資料流**：訂閱 `/scan` → 改掉兩段角度 → 發布到 `/scan_filtered`。
Nav2 的代價地圖（`navigation.yaml`）讀的是 `/scan_filtered`，所以不會把柱子當障礙。

**算算看**：柱子在車身座標 x=0.41、y=±0.12，雷射在 x=0、y=0。
角度＝atan(0.12 / 0.41) ≈ 0.284 弧度 ≈ 16.3°，跟程式註解一致。
雷射每圈 360 點、每點 1°，所以每邊大約過濾掉 7～8 個點。

> 💡 README 說「在**短距離內**遮罩」，但這版程式其實**不管距離、整段角度都遮掉**。
> 這代表那兩個方向遠處的真障礙也會被忽略。這是你可以練習改進的地方（見第 12 章練習 3）。

### 5.5 `amr_forklift/amr_behavior_tree.py`——行為樹自主節點（最核心的觀念）

#### 什麼是行為樹？

行為樹每秒「tick（滴答）」好幾次，每次從樹根往下問：「現在該做什麼？」
每個節點回答三種狀態之一：

- `SUCCESS`（成功）
- `FAILURE`（失敗）
- `RUNNING`（還在做，下次再問我）

兩種最重要的組合節點：

| 組合節點 | 規則 | 比喻 |
| --- | --- | --- |
| **Selector（選擇器，`?`）** | 由左到右試，**第一個不是 FAILURE 的就停** | 「先試 A，不行再試 B，再不行試 C」 |
| **Sequence（序列，`→`）** | 由左到右做，**有一個不是 SUCCESS 就停** | 「先做 A，A 成功才做 B」 |

#### 本專案的樹

```
? AGV_Main_Decision_Tree（Selector，優先權由左到右）
├── → Safety_Emergency_Sequence（緊急停止分支）
│     ├── CheckSafety      有危險嗎？有 → SUCCESS；沒有 → FAILURE
│     └── EStopAction      發布速度 0 → 停車
├── → Battery_Charging_Sequence（充電分支）
│     ├── CheckBattery     電壓 ≤ 11.0V？是 → SUCCESS
│     └── BatteryChargingAction  停車，每秒電壓 +0.5V，到 14.2V 才 SUCCESS
└── PatrolAction（預設：巡邏）
      永遠 RUNNING：直走 5 秒、轉彎 3 秒，一直循環
```

**閱讀重點**：

1. **優先順序**＝擺放順序。安全 > 電量 > 巡邏。只要有危險，後面兩個根本不會被問到。
2. 注意 `CheckSafety` 的命名有點反直覺：它在「**有危險**」時回 SUCCESS，意思是「確認有危險這件事成立」，這樣才會接著執行停車。
3. **黑板（Blackboard）**：行為樹節點之間共享資料的地方。ROS 訂閱的 callback 把收到的值寫進黑板，
   行為樹節點從黑板讀。這樣「收訊息」和「做決策」就分開了。

```python
self.create_subscription(Float32, 'battery_voltage', self.battery_callback, 10)
self.create_subscription(Bool,    'safety_hazard',   self.safety_callback, 10)
...
def battery_callback(self, msg):
    self.blackboard.set("battery_voltage", float(msg.data))
```

1. **計時器驅動**：`self.create_timer(0.2, self.tick_tree)` → 每 0.2 秒 tick 一次（5 Hz）。

#### 算算巡邏軌跡

`PatrolAction` 每次 tick 把 `step` 加 1，在 0～39 之間循環：

- step 0～24（25 次 × 0.2 秒 = **5 秒**）：前進 0.3 m/s → 走 **1.5 公尺**
- step 25～39（15 次 × 0.2 秒 = **3 秒**）：原地轉 0.6 rad/s → 轉 **1.8 弧度 ≈ 103°**

所以機器人會走出一個「不太規則的多邊形」，不會剛好是正方形。

#### 怎麼觸發另外兩個分支？（模擬中要自己發訊息）

模擬裡**沒有**電池或氣體感測器，所以除非你手動發訊息，機器人會永遠巡邏：

```bash
# 觸發緊急停止
ros2 topic pub --once /safety_hazard std_msgs/msg/Bool "{data: true}"
# 解除
ros2 topic pub --once /safety_hazard std_msgs/msg/Bool "{data: false}"
# 模擬低電量 → 停車充電，電壓每秒 +0.5V，約 7 秒後恢復巡邏
ros2 topic pub --once /battery_voltage std_msgs/msg/Float32 "{data: 10.5}"
```

> ⚠️ 這個行為樹是「**示範用**」的：巡邏是直接對 `/cmd_vel` 下速度，**不經過 Nav2，不會避障**，
> 也不會繞過牆。真車的任務邏輯（取放貨、障礙守衛）不在 repo 裡。

### 5.6 `launch/gazebo.launch.py`——開模擬的總開關

依序啟動：

| 動作 | 說明 |
| --- | --- |
| `SetEnvironmentVariable GAZEBO_RESOURCE_PATH` | 告訴 Gazebo 去哪裡找「NEBULA」貼紙材質 |
| `gzserver ... nebula_arena.world` | Gazebo 物理引擎（無畫面），載入場地 |
| `gzclient` | Gazebo 的 3D 畫面 |
| `robot_state_publisher` | 讀 `model.xacro`（帶 `is_sim:=true`），把機器人模型發到 `/robot_description`，並發出零件之間的固定 TF |
| `spawn_entity.py` | 把機器人放進 Gazebo，位置 (x=-6.0, y=-3.8, z=0.15)，朝向 -90°（面朝 -y 方向） |
| `rviz2` | 開 RViz，用 `rviz/config.rviz` 的版面 |
| `scan_filter_node` | 雷射過濾 |

`use_sim_time: true` 的意思是：大家都用 **Gazebo 的模擬時鐘**，不用電腦的真實時間。
模擬跑慢的時候，所有節點的時間一起變慢，計算才不會亂掉。

### 5.7 其他 launch 檔——四種玩法

| 檔案 | 需要先開 Gazebo？ | 做什麼 | 適合 |
| --- | --- | --- | --- |
| `slam.launch.py` | 是 | 只開 SLAM Toolbox，邊開邊畫地圖 | 第一次建地圖 |
| `slam_nav.launch.py` | 是 | SLAM＋Nav2（不含 AMCL、不含 map_server） | **最推薦**：不用存地圖、不用手動設初始位置，直接在 RViz 點目標 |
| `nav2.launch.py` | 是 | Nav2 完整 bringup：map_server 讀 `maps/map_latest.yaml`＋AMCL 定位＋規劃 | 用存好的地圖導航 |
| `nav2_map.launch.py` | 是 | 同上，用 bash 呼叫 `ros2 launch` 的寫法 | 同上（兩者擇一） |
| `behaviors.launch.py` | 是 | 開行為樹節點 | 看行為樹巡邏 |

`slam_nav.launch.py` 的檔頭註解（土耳其文）翻成中文是：

> SLAM 和 Nav2 一起跑——不用 AMCL、不用手動設 2D Pose Estimate。
> slam_toolbox 持續做雷射比對，自動且精準地產生 map→odom。所以不用「存地圖／載地圖」的來回、
> 不用手動設初始姿態、也沒有 AMCL 的角度誤差。用法：Gazebo 開著時執行，
> 然後在 RViz 直接按「Nav2 Goal」給目標，機器人就會走過去。先用遙控繞一下讓地圖長出來。

### 5.8 `config/navigation.yaml`——Nav2 全套設定（最長的設定檔）

不用一次全懂，抓幾個關鍵數字：

| 區段 | 關鍵參數 | 意義 |
| --- | --- | --- |
| `amcl` | `max_particles: 2000`、`laser_model_type: likelihood_field` | 用 500～2000 個「猜測點」估計機器人在地圖哪裡 |
| `bt_navigator` | `NavigateToPoseNavigator` | Nav2 內部**也用行為樹**決定「規劃→跟隨→卡住就恢復」 |
| `controller_server` | `controller_frequency: 20.0`、`DWBLocalPlanner` | 每秒 20 次算「下一步速度」 |
| DWB | `max_vel_x: 0.26`、`max_vel_theta: 1.0` | 最快 0.26 m/s 直走、1 rad/s 轉彎 |
| DWB | `critics: [RotateToGoal, Oscillation, BaseObstacle, GoalAlign, PathAlign, PathDist, GoalDist]` | 對每條候選軌跡打分數的「評審」，例如離路徑多遠、會不會撞、會不會來回抖 |
| `local_costmap` | `footprint: [[0.40,0.25],[0.40,-0.25],[-0.40,-0.25],[-0.40,0.25]]` | 機器人是 0.8 × 0.5 公尺的長方形，不是圓形 |
| `local_costmap` | `observation_sources: scan left_sensor right_sensor`、`topic: /scan_filtered` | 障礙物來源＝過濾後雷射＋前方兩個測距感測器 |
| `planner_server` | `NavfnPlanner` | 全域規劃器，經典的 Dijkstra／A* 演算法 |
| `behavior_server` | Spin、BackUp、DriveOnHeading、Wait | 卡住時的「恢復動作」：原地轉、倒車、等待 |

**DWB 是怎麼運作的？**（Dynamic Window Approach，動態視窗法）
每次控制週期，它在「目前速度附近、加速度做得到的範圍內」取樣很多組（前進速度, 旋轉速度），
模擬每組往前開 1.7 秒（`sim_time`）會走到哪，交給評審打分，挑最高分的那組送去 `/cmd_vel`。

### 5.9 `config/slam_toolbox_mapping.yaml`

- `mode: mapping`：建圖模式（另一種是只定位的 localization）
- `resolution: 0.05`：地圖每格 5 公分
- `scan_topic: /scan`：SLAM 用**原始**雷射（不是過濾後的）
- `base_frame: base_footprint`：註解寫「關鍵修正：避免 TF 衝突」
- `minimum_travel_distance: 0.05`、`minimum_travel_heading: 0.05`：走 5 公分或轉 0.05 弧度才更新一次地圖

### 5.10 真車才用的三個設定（模擬沒用到）

| 檔案 | 用途 | 為什麼模擬沒用 |
| --- | --- | --- |
| `ekf.yaml` | `robot_localization` 的 EKF：融合 `/wheel_odom` 的前進速度＋`/imu/data_fused` 的偏航角與角速度 | 模擬裡 Gazebo 直接發 `/odom` 和 odom→base_footprint TF，沒有啟動 EKF |
| `madgwick_filter.yaml` | 把 IMU 原始資料（`/imu/data_raw`）算成姿態 | 同上，沒有 launch 會啟動它 |
| `controller.yaml`＋`ros2_controller.xacro` | ros2_control 差速控制器；硬體外掛 `NebulaHardware` 透過 `/dev/ttyACM0`（Arduino）控制 | 模擬用 Gazebo 的差速外掛代替；而 `NebulaHardware` 外掛程式碼不在 repo |

**`ekf.yaml` 的 15 格布林陣列怎麼看？** 順序是：

```
x  y  z  roll pitch yaw  vx vy vz  vroll vpitch vyaw  ax ay az
```

- IMU 只取 `yaw`（第 6 格）和 `vyaw`（第 12 格）→ 「方向」交給 IMU
- 輪子只取 `vx`（第 7 格）和 `vyaw`（第 12 格）→ 「前進速度」交給輪子

這就是「各取所長」：輪子量前進距離準，IMU 量轉角準。`two_d_mode: true` 表示只考慮平面。

### 5.11 `models/nebula_urdf/model.xacro`——機器人長什麼樣

| 零件 | 尺寸／位置 | 關節類型 |
| --- | --- | --- |
| 車身 `base_link` | 0.797 × 0.494 × 0.201 公尺，30 kg | 用 fixed 接在 `base_footprint` 上方 0.125 m |
| 左右驅動輪 | 半徑 0.075 m、寬 0.045 m、2 kg；左右間距 0.415 m | `continuous`（可無限旋轉） |
| 四個萬向輪 | 在 (±0.35, ±0.22)，可水平自轉＋滾動，有 0.025 m 拖曳偏移 | 兩個 `continuous` 串接 |
| LiDAR | 車身中央上方 0.2 m | `fixed` |
| IMU | 車身中央上方 0.09 m | `fixed` |
| 前方測距感測器 | (0.431, ±0.12) | `fixed` |
| 叉架 `forklift_mast_link` | 兩根 0.6 m 高的柱子在 x=0.41 | `fixed` |
| 叉子 `forklift_carriage_link` | 兩根 0.35 × 0.15 m 的叉子 | **`prismatic`（直線滑動）**，可升 -0.02～0.3 m |

**有趣的註解**（原文土耳其文，翻譯）：

- 輪子重量：「改成真實的 2.0 kg（舊的 10 kg 很離譜 → 轉動慣量太大 → 打滑＋停下來會滑）」
- 萬向輪：「真正會轉的萬向輪……拖曳偏移讓機器人移動時自己對齊」

`properties.xacro` 定義了三個巨集，用物理公式算**慣性矩**（物體多難被轉動）：

- 長方體：Ixx = m/12 × (h² + w²)
- 圓柱：Ixx = m/12 × (3r² + h²)
- 球：I = 2/5 × m × r²

最後一段 `<xacro:if value="$(arg is_sim)">`：**只有在模擬時**才載入 `gazebo_plugins.xacro`。
這是「同一份模型，模擬和真車共用」的常見技巧。

### 5.12 `models/nebula_urdf/gazebo_plugins.xacro`——讓模型在模擬器裡「活起來」

| 外掛 | 檔案 | 輸入 | 輸出 |
| --- | --- | --- | --- |
| 差速驅動 | `libgazebo_ros_diff_drive.so` | `/cmd_vel` | 轉動左右輪；發 `/odom` 和 odom→base_footprint TF |
| LiDAR | `libgazebo_ros_ray_sensor.so` | — | `/scan`（360 點、0.15～10 m、雜訊標準差 1 cm） |

| 右前測距 | 同上 | — | `/right_sensor/scan` |
| IMU | `libgazebo_ros_imu_sensor.so` | — | `/imu/data_raw`（50 Hz、加了雜訊） |

`odometry_source: encoder` 的註解說：用「輪子轉動」算里程計（穩定、接近真車），
而不是用 Gazebo 的真實位置（會反映接觸抖動 → 漂移）。

### 5.13 `worlds/nebula_arena.world`——比賽場地

純 SDF 方塊組成，不依賴外部模型：外牆 7 段、左右隔牆、左右閘門（底座＋橫桿）、
起點區、A1～A3 與 B1～B3 六個工作區、地上的引導線、9 個 QR 碼（q1～q9，真車用相機讀）。

### 5.14 `maps/map_latest.pgm` 與 `.yaml`

- `.pgm` 是灰階圖片：白＝空地、黑＝牆、灰＝未知。大小 202 × 322 像素。

### 5.15 `rviz/config.rviz`

## 8. 從 README 學工程思維（作者踩過的八個坑）

這些都是「教科書不會教、真車才會遇到」的問題，很值得讀：

1. **定位系統整個壞掉**：地圖在機器人靜止時自己轉 20～30°。作者一層層追：
   車頭方向與輪子方向的正負號錯、輪距設錯（角度里程計全歪）、IMU 資料不穩，
   最隱蔽的是**編碼器計數錯誤**：上升緣與下降緣都算，2 個 tick 才等於 1 步，
   所以距離和角度都放大約 2 倍。**每個修正都先在 Gazebo 驗證**。
2. **障礙物「停下等待」而不是繞道**：比賽規定擋住要停、清空後走**同一條路**。
   Nav2 預設會重新規劃，所以作者寫了「守衛節點」：把整條路徑存起來，有障礙就取消追蹤，
   清空後重新送出同一條路徑。（程式不在 repo）
3. **USB 不穩改走 WiFi/TCP**：USB 埠會改名、udev 規則衝突。改成 ESP32 連 WiFi、當 TCP 客戶端，開機順序無所謂、會自動重連。
4. **馬達安靜又平順**：Arduino 預設 PWM 約 490 Hz（會有嗡嗡聲），改成直接設定計時器暫存器的 **20 kHz**；
   每個輪子用 **PID＋前饋**（靜摩擦＋黏滯摩擦項）控制。
5. **CPU 100%、移動一頓一頓**：原因是 QR 碼讀取節點**不小心跑了兩份**。
6. **雷射看到自己的叉子**：就是 `scan_filter_node` 的由來。
7. **教點介面**：不輸入座標，而是把車開到定點按「記住這裡」；地圖每 2～3 秒推到網頁並疊上即時雷射，
   雷射跟牆對齊就代表定位正常。
8. **在 4 GB RAM 筆電上開發**：整套 ROS 2＋Gazebo＋RViz 在小電腦上跑，逼自己注意資源用量。

**共通心法**：「**先模擬、再上真車**」、「**一層一層驗證，不要一次改很多**」、「**用看得見的證據（雷射疊地圖）確認系統健康**」。

| 1 | `slam.launch.py` 註解 | 說「Madgwick 和 EKF 由 gazebo.launch.py 啟動」 | 實際上 `gazebo.launch.py` 沒啟動它們；`ekf.yaml`、`madgwick_filter.yaml` 在模擬裡都沒用到 |
| 2 | `config/behaviors.yaml` | 空檔案 | 沒作用 |
| 3 | `CMakeLists.txt` | Python 安裝路徑寫死 `python3.10` | 換 Python 版本時模組裝錯位置（不影響 launch） |
| 4 | `controller.yaml` | `use_stamped_vel: true`，但模擬的 diff_drive 外掛吃的是一般 `Twist` | 真車與模擬的速度訊息格式不同 |
| 5 | `ros2_controller.xacro` | 用到 `NebulaHardware` 外掛 | 外掛原始碼不在 repo，真車模式無法建置 |

| 7 | `amr_behavior_tree.py` | 巡邏直接發 `/cmd_vel` | 不避障；與 Nav2 同開會互搶 `/cmd_vel` |
| 8 | `amr_behavior_tree.py` | 用舊式 `py_trees.blackboard.Blackboard()` | py_trees 2.x 推薦用 `Client` 並註冊鍵值；舊寫法仍可用但不嚴謹 |
| 9 | 地圖與出生點 | 出生點 (-6.0, -3.8)，地圖 y 範圍 -2.15～13.95 | 出生點在 `map_latest` 的範圍外，用 `nav2.launch.py` 時 AMCL 的初始位置需要手動設；建議改用 `slam_nav.launch.py` |
| 10 | `package.xml` | 沒列 `gazebo_ros`、`nav2_bringup`、`slam_toolbox`、`py_trees`、`xacro`、`rviz2` | `rosdep install` 不會自動幫你裝齊，要手動裝 |
| 11 | `amr_behavior_tree.py` 的 `EStopAction` | 呼叫 `self.logger.critical(...)`，但 py_trees 的 Logger 沒有 `critical` | **實測：一觸發緊急停止，節點就 `AttributeError` 當掉**，停車指令沒送出。改成 `logger.error` 即可（見 [02-逐步實作講解](02-逐步實作講解.md) 步驟 7） |

> 要先 `export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`（見 02 步驟 6）。

| 週 | 目標 | 具體做法 |

## 12. 練習題（由淺到深）

1. **改巡邏路線**：修改 `PatrolAction`，讓機器人走出正方形（提示：轉 90° 需要 π/2 ÷ 角速度 秒）。
2. **加一個新分支**：在行為樹加一個「溫度過高就減速」的分支，訂閱 `/temperature`（Float32）。
3. **改進過濾節點**：只在距離小於 0.6 公尺時才過濾柱子方向，遠處的障礙保留。
4. **調導航速度**：把 `navigation.yaml` 的 `max_vel_x` 從 0.26 改成 0.4，觀察到目標時會不會衝過頭。
5. **讓行為樹走 Nav2**：把 `PatrolAction` 改成呼叫 Nav2 的 `NavigateToPose` action，依序走 A1→B1→起點。
6. **實作「停下等待」守衛**：當 `/left_sensor/scan` 或 `/right_sensor/scan` 距離 < 0.5 m 時發布 `/safety_hazard true`，清空後發 `false`。
